# Internationalization (i18n)

Issue #95. This document is the reference for the message layer, the locale
mechanics, and — most importantly for a Stellar app — how a 7-decimal token
amount survives being displayed in German.

Code lives in `frontend/lib/i18n/`:

| File | Role |
| --- | --- |
| `locales.ts` | Locale registry, `<dir>` table, `Accept-Language` matching |
| `messages/en.ts` | English catalog — the source of truth for keys |
| `messages/de.ts` | German catalog, typed `Record<MessageKey, string>` |
| `messages/index.ts` | Catalog registry + the key → parameter type contract |
| `messages/cognates.ts` | The only keys allowed to be identical across locales |
| `format.ts` | ICU compile cache + `formatMessage` |
| `amounts.ts` | BigInt-exact amount formatting and locale-aware parsing |
| `parse-error.ts` | Parse failure → user-facing message |
| `provider.tsx` | Client `useLocale()` (cookie + `router.refresh()`) |
| `server.ts` | Server-side locale resolution for the first render |
| `components/LocaleSwitcher.tsx` | The `<select>` that changes it |

---

## 1. Why ICU MessageFormat, and not the alternatives

The catalogs use ICU MessageFormat (`intl-messageformat` 12.1.3), the
implementation behind FormatJS and the specification CLDR itself is built on.
Three properties decide it, and each rules out a cheaper option:

**Grammatical number is a property of the language, not of the component.**
`{count, plural, =0 {kein Stream} one {# Stream} other {# Streams}}` lets
German use its two plural forms and English use its own, with the *message*
choosing. Alternatives:

- **Template strings / `.d.ts`-free string concatenation** ("`Discovered ` +
  n + ` stream(s)`") cannot express plural categories beyond ad-hoc `n === 1 ?
  …` in JSX. Arabic has six, Russian three grammatical ones; every such rule
  would live in a component instead of the catalog a translator owns.
- **`Intl.NumberFormat` alone** formats *numbers*, not *sentences*. It gives no
  plural/select branches, no `select` for a status word, and it would force us to
  pass amounts as `number` — which is the precision bug this layer exists to
  prevent (§3).
- **`Intl.PluralRules` hand-rolled** is ~40 lines of our own `select`/`plural`
  evaluator plus a message parser. That is a subset of ICU, rewritten, without
  the tooling that validates it.

**Named placeholders let word order move.** German puts the verb second-to-last:
`"{amount} aus Stream #{id} abgehoben."` reverses English's
`"Withdrew {amount} from stream #{id}."` Any positional scheme (`%s`, `{0}`)
couples the translation to the English order; named arguments do not. That is
also why the catalog gate diffs *placeholder names* rather than raw text.

**Choice by value.** `{unit, select, tokens {Tokens} other {unit}}` covers the
"same slot, different noun phrase" cases without an `if` in JSX.

Rejected heavier options: `react-intl` / `next-intl` / `Lingui` bring their own
provider, extraction pipeline, and message-id conventions. We need typed keys and
a compiler-checked catalog, which `intl-messageformat` gives in one dependency
with no framework coupling, no service worker, and no build-time codegen step —
important because this repo's CI gate for the frontend is a straight
`lint → typecheck → test → build → audit`.

Gettext-style (`.po`/`.mo`) catalogs were rejected because our catalog is the
*type*: `MessageKey`
is `keyof typeof en`, and a JSON/PO file would need a codegen step to produce
that type. The trade-off is documented in §6 (no translator GUI; editors edit TS).

## 2. Locale resolution

Order of precedence, implemented in `server.ts::resolveRequestLocale`:

1. `streampay_locale` cookie — an explicit, past choice.
2. The top-quality match in `Accept-Language` — a German browser gets German on
   the very first request, with no JavaScript.
3. `DEFAULT_LOCALE` (`en`).

`matchLocaleTag` strips the region: `de-AT` → `de`, `pt-BR` → no match (we do not
ship Portuguese). `SUPPORTED_LOCALES` is the only list to change when adding one.

**Why a cookie and not `localStorage`.** `<html lang>` and `dir` must be correct
in the *first* HTML document. A client-side switch would ship English markup to
a German user and then swap it: a flash of the wrong language, and an
accessibility defect — screen readers choose their voice from the document
`lang` at parse time, so a late patch is too late (WCAG 3.1.1). The switcher
therefore writes the cookie and calls `router.refresh()`, so the server stays the
single owner of the locale; there is no client copy to disagree with the markup
it rendered.

Consequence worth knowing: reading `cookies()`/`headers()` makes the routes
server-rendered per request (`ƒ` in `next build` output) instead of
prerendered. That is inherent to a correct first paint and matches how the rest
of this app already works. It also requires that we are not doing a static
export — `next.config.ts` has no `output: "export"`.

Fallback behaviour when a catalog entry is broken: outside production
`formatMessage` **throws** with the key and locale, so a bad translation cannot
ship silently; in production it degrades to English, then to the key, because a
malformed string must not blank out a claim button.

## 3. The Stellar trap: 7 decimals and floating point

The requirement is that localized display must not break precision, and localized
input parsing must not break on comma vs dot. Display first.

`Number(90071992547409933n) / 1e7` is *wrong* — past 2^53 the float cannot even
represent the integer it started from, so the error is in the units digit and no
`toFixed()` recovers it. StreamPay amounts are unsigned 128-bit on-chain, so this
is reachable with real balances. The rules `amounts.ts` enforces:

- **The value never leaves `BigInt`.** `formatTokenAmount` splits `abs / 10^d`
  and `abs % 10^d` as *digit strings*, then groups and punctuates by hand.
- **`Intl` is consulted for *shape*, never for the value.** `localeShape()`
  formats the probe `123456789012.5` (exactly representable) and reads
  `formatToParts` to learn the decimal character, the grouping character, the
  minus sign, the primary/secondary group sizes, and the locale's digit glyphs.
- **Amounts enter ICU as strings.** The catalog takes `{amount}` and `{percent}`
  as `string` in `MessageParams`, which is a compile error if a call site tries
  to pass a `number`. Counts and percentages may use ICU's own `number`
  formatting; token amounts may not.
- `maxFractionDigits` exists for *display* copy only (the social-preview title
  caps at 4). Nothing that gets signed, quoted, or compared uses it.

Proof: `lib/i18n/amounts.test.ts` (30 cases) covers the exact 7th decimal
(`1n → "0.0000001"`), above-2^53 values, `en` vs `de` grouping
(`1_234_567_890_123n`), non-Latin digits (`ar-u-nu-arab` renders and round-trips
Arabic-Indic glyphs), `sv` space grouping, and Indian 3-then-2 grouping
(`1,23,45,678.9012345`). `catalog.spec.ts` re-proves the exactness *through the
message layer*, and asserts that the float path disagrees.

## 4. Comma vs dot: what the parser decides

`parseTokenAmount(input, locale, { decimals, allowNegative })` returns
`{ ok: true, value: bigint }` or `{ ok: false, reason }`. With `D` = the locale's
decimal separator and `G` = its grouping separator:

| Input shape | Read as | Example |
| --- | --- | --- |
| both `.` and `,` present | **rightmost one is the decimal separator**, the other is grouping | `"1.234,56"` and `"1,234.56"` → `1234.56` in *either* locale |
| one character repeated | grouping | `"1.000.000"` → `1000000` |
| one character, and it is `D` | decimal — `D` wins over the "3 digits means grouping" heuristic | `"1,000"` in `de` → `1.0`, not `1000` |
| one character, and it is `G` | grouping **iff exactly 3 digits follow**, else decimal | `"1.000"` in `de` → `1000`; `"1.00"` in `de` → `1.00` |
| one character, neither `D` nor `G` | decimal | `"1,5"` in `en` → `1.5` |

Then, and this is the point of the whole table:

- More fraction digits than the field's `decimals` → `too-precise`. We **refuse
  instead of rounding**; a rounded deposit is a different on-chain amount than
  the one the user meant to type.
- Malformed groups (`"1,2345"`) → `bad-grouping`. A repeated decimal character
  (`"1,5,5"` in `de`) → `ambiguous-separator`.
- Locale digit glyphs fold to ASCII first; NBSP/thin/space grouping is accepted
  so a copied `"1 000 000"` parses; junk (`"1e7"`, `"0x10"`, `""`) is rejected.

The smallest-unit field on the create form (`StreamForm`) passes `decimals: 0`,
so grouping is accepted, `"1.000"` in German means one thousand units, and any
fraction is refused rather than truncated. Its input is `type="text"` with
`inputMode="numeric"` — deliberately *not* `type="number"`, because an HTML
number input is locale-fixed to `.` and would make the German comma untypeable.

## 5. RTL

No shipped locale is RTL yet; the architecture is RTL-ready and documented here
so that adding `ar` is a data change, not a refactor:

- `LOCALE_DIR: Record<Locale, "ltr" | "rtl">` is the single source; the root
  layout renders `<html lang={locale} dir={localeDir(locale)}>`, so direction is
  correct on the first byte of HTML.
- Layout uses flow-relative constructs. New CSS should use logical properties
  (`margin-inline-start`, `padding-inline-end`, `inset-inline-start`,
  `text-align: start`) rather than `left`/`right`, and flex/grid rows flip
  automatically under `dir="rtl"`.
- **Never** flip an icon or an amount by hand in a component: bidi handling of
  `#1234` inside Arabic prose is the browser's job via `dir` plus, where needed,
  an `unicode-bidi: isolate` wrapper. Stellar addresses and contract ids are
  LTR tokens embedded in RTL text — wrap them in `<bdi>` when adding an RTL
  locale.
- `ar-u-nu-arab` is already exercised in `amounts.test.ts` (Arabic-Indic digits
  format and parse back), which is the part most implementations get wrong.
  Checklist for
  the first RTL locale: add to `SUPPORTED_LOCALES` + `LOCALE_DIR` as `rtl`, add
  the catalog, run the snapshot suite, then audit `components/*.css` for
  physical properties.

## 6. Contributor workflow (adding or editing a message)

1. Add the key and English text to `messages/en.ts`. The catalog is a TS module
   with `as const`, so `MessageKey` is derived from it — no codegen.
2. Add the same key to `messages/de.ts`. Because that file is typed
   `Record<MessageKey, string>`, a missing or extra key fails `npm run typecheck`
   in every locale. Do the same for any locale you add.
3. If the message interpolates, declare the parameter types in `MessageParams`
   (`index.ts`) *and* a fixture in `MESSAGE_SAMPLES`. The mapped type makes the
   second step a compile error if you skip it, and the test suite proves that the
   set of declared parameters equals the set of messages that actually contain
   placeholders. Amounts are `string`, by rule (§3).
4. If the German text is *intentionally* identical to English (a brand name, a
   unit symbol), add the key to `messages/cognates.ts`. Anything else that still
   matches English fails the build — that is the untranslated-key check the
   issue asks for: `catalog.spec.ts` reports
   `untranslated = keys where a non-en catalog equals en and the key is not in
   COGNATE_SET` and asserts it is `[]`. It runs on every `npm test`.
5. Update snapshots deliberately, never blindly: run
   `npx vitest run -u lib/i18n/catalog.spec.ts` and *read the diff*. The snapshot
   is the whole rendered catalog per locale, so a dropped placeholder or a
   collapsed plural arm shows up as a diff line.
6. Placeholders are the one thing a translation must never rename. The gate reads
   them from the **parsed ICU AST** (`getAst()`), not from a regex, because a
   regex cannot tell `{unit, select, tokens {Tokens} …}`'s case bodies from
   arguments and would fail a correct translation.

Translation memory / vendor GUIs are deliberately out of scope: catalogs are
source files reviewed in a PR, which keeps a translator's change under the same
type check and snapshot gate as any other edit.

## 7. Coverage

Localized surfaces: root layout (document `lang`/`dir`, skip link, metadata),
`NetworkBadge` (including its ARIA strings), the home page, the payment-link page
and its `generateMetadata`, and the create-stream form including deposit parsing.
Remaining English (tracked follow-ups, no code coupling — they can be converted
key by key): `StreamList`, `BatchStreamForm`, `/stream/[id]`, `/address/[addr]`,
`/simulator`, `/docs`, `/analytics`, `/listings`, and `describeError`'s
contract-error strings.

## 8. Test map

| Suite | Runner | Proves |
| --- | --- | --- |
| `lib/i18n/amounts.test.ts` | `node --test` | Exact 7-decimal display, above-2^53 values, every comma/dot precedence rule, glyph folding, refuse-not-round |
| `lib/i18n/catalog.spec.ts` | `vitest` | Per-locale catalog snapshots, ICU plural/select, stroop exactness through the message layer, key + placeholder integrity, the untranslated-key gate, a message for every rejection reason, locale detection |

`frontend/package.json`'s `test` script runs **both** (`node --test && vitest
run`). This matters: the two runners are disjoint by design (`.test.ts` is the
Node suite, `.spec.ts` the vitest suite, per `vitest.config.mts`), and a single
`"test"` key in that script block silently disabled the vitest half.
